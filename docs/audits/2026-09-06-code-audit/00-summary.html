What the codebase is like

The shape of the system is sound. Every server route uses the service-role Supabase key, so the code itself is the tenant wall, and that wall is mostly well built: schoolId always comes from the signed session and never from the request body, the parent surface enforces authorizedChildIds in all twelve child routes, all 83 super-admin routes are guarded, both Stripe webhooks verify signatures on the raw body, there is no SQL injection anywhere, no service-role key leaks into browser code, and the newer modules (CMS, Lens, Potato, the Tracking Engine, the evaluation module) are the reference quality the older ones should converge on.

The holes are of three kinds, and they repeat. First, authentication without authorisation: a route checks that you are logged in but not that you are a principal. Second, a scoping check that only runs on one branch of a handler. Third, an old layer that was never switched off: permissive database policies from June, a legacy Whale route set, a beta flag. None of these is exotic. All of them are cheap to fix and cheap to prevent with a handful of shared helpers, which is the structural proposal at the end.

Do today, in this order

1 · Check whether the database is open to the internet Critical

In June, supabase/migrations/096_rls_policies.sql created "allow everything" policies on montree_schools, montree_classrooms, montree_teachers, montree_children, montree_parents, montree_parent_children and montree_parent_invites. Because they name no role, they apply to the public anon key, and that key ships inside the montree.xyz JavaScript. Later clean-ups (277, 313, 337) dropped policies with similar names but not these seven. Two reviewers tried to prove the policies were never applied and could not: migration 275's linter list shows RLS was already on for these tables, and the only file that ever turned it on is 096. If they are live, every child's name, birthday and notes, every parent's email and phone, every teacher's login code and every parent invite code on the platform is a public REST endpoint, with no log line in the app because the traffic never touches it.

Run this in the Supabase SQL editor first. Any row back means the hole is real.

SELECT tablename, policyname, roles, cmd, qual
FROM pg_policies
WHERE schemaname = 'public'
  AND tablename LIKE 'montree_%'
  AND (qual IS NULL OR qual = 'true');

2 · Give the super-admin its own signing key High

lib/verify-super-admin.ts signs the platform-owner token with SUPER_ADMIN_JWT_SECRET, but if that variable is missing it silently falls back to SUPER_ADMIN_PASSWORD. Your own notes (CLAUDE.md line 2359 and two July handoffs) still list "confirm the secret is set in Railway" as open, and nothing later closes it. A token signed with a human password can be cracked offline from one captured token, and then anyone can mint god-mode tokens forever, because nothing can revoke them (item 6 below).

In Railway → happy-flow → whale-class → Variables, add SUPER_ADMIN_JWT_SECRET with a long random value (run openssl rand -base64 48 on the Mac and paste the output). Then we delete the two fallbacks in code so a missing variable fails loudly instead of degrading quietly.

3 · Close the platform-wide overwrite High

GET /api/montree/admin/backfill-guides?all=true checks school ownership only when a classroom id is given. With all=true it rewrites the guide text, presentation steps, aims and parent descriptions for every classroom on the platform from the canonical files, and any logged-in teacher can trigger it — including by accident, since it is a GET that an image tag can fire. This is a five-line fix (gate the all branch on super-admin and make it POST). It goes out with the batch below, but I want it named on the "today" list because it is the one confirmed cross-tenant write reachable from an ordinary login.

The Tracking Engine: the core, one day old

The reviewer executed the pure engine directly against synthetic terms, and the good news is real: the ladder, the name reader, the 40-word summary cap, the ribbon and the summary templates all match the constitution word for word, the new tracker screen round-trips its writes correctly, and the simulated-term harness from the plan exists and is thorough. The one-door rule holds — no undetected writer to montree_child_progress exists. Four things break it, and three of them would have been caught by a single missing test.

Corrections vanish on replay Critical

The door journals source as the caller sent it and reason as null, instead of the engine's decision. The old P/P/M picker in progress/update (eight legacy surfaces) downgrades with source:'teacher_update'; on replay applyEvent rejects a backward move without a correction reason, so the rebuilt ledger says mastered while the cached row says practising. Guru's correcting_downward has the same defect. Proven by running the real door. The fix is three lines — carry engineEvent.source and engineEvent.reason into the journal row — and the reviewer applied it and watched the failing cases pass.

Duplicate-merge destroys progress across schools Critical

curriculum/duplicates renames and deletes montree_child_progress rows by work_name with no child or classroom filter, and it is reachable by any teacher, not just super-admin. Merging two "Pink Tower" entries in one classroom rewrites every child's Pink Tower record on the platform. It is the one file the one-door test exempts. Fix: fetch the classroom's child ids once and add .in('child_id', ids) to the five statements; journal the delete as a real transition.

The class tracker takes 29 seconds of CPU High

Measured on 22 children × 30 events each: every derivation re-replays the whole journal per child, and flags(), englishSummary() and planLanguageCell() each cost 6–10 s. A WeakMap memo on replay alone only gets to 10 s; adding a cutoff-day cache brings the same request to 35 ms. Both changes are additive and pure.

Days and weeks are cut at UTC midnight, which is 08:00 in Beijing High

The same-day de-dupe and the Monday week buckets use hard UTC; lib/montree/school-time.ts is used by fourteen routes and by nothing in the engine. For you the broken band is 00:00–08:00, so it mostly bites early-morning ticks; for a school west of UTC it splits mid-afternoon. Fix: carry the school timezone in the ledger and use it in dayOf/mondayOf; write a local_day column from the door so the index can match.

Smaller but real

The journal append is best-effort after the cache row commits, so the cache can outrun its source of truth and nothing tells the caller. Resolving a review-queue item writes the raw name, creating a second row per work_key (no unique index exists on (child_id, work_key)). Two unresolvable names in one batch collide on the dedup index and the whole batch is dropped as "non-fatal". The SQL rebuild function in migration 346 disagrees with the JS rebuild and has zero callers — delete one. The guard test scans one table with literal strings; montree_child_focus_works has 15 direct write sites and the events and review-queue tables are unguarded. Health rule 10 will flag every row stamped by backfill-work-keys.mjs and the rebuild cannot fix them.

The decisive missing test is a journal round-trip: door write → read back → replay → assert equals cache. The reviewer wrote it (six cases, four fail today, five pass with the three-line fix) and it is in the report, ready to drop into tests/progress/.

Proposals — the structural fixes

These are the changes that stop the same class of bug returning. I would sequence them after the two batches above.

Three shared helpers, then a lint that enforces them

verifyPrincipalRequest() for anything under admin/; requireClassroom(auth, classroomId) that returns 404 unless the classroom belongs to the session's school, replacing the hand-rolled checks that currently live on one branch of a handler; and parseBody(schema) with zod, because right now zero routes validate their body shape. Then extend scripts/audit-tenant-scoping.mjs to fail on any route under admin/ that lacks the principal guard, and any route that reads classroom_id or child_id from the request without calling a verify helper.

Make CI actually run

The repo has 59 test files, two audit scripts and a TypeScript error budget, and none of them run on push: the three workflows are DNS guard, engagement cron and tracking health. The TS ratchet baseline is 5,233 against a reality about six times lower, so it cannot fail. Add one workflow: vitest run, both audit scripts, and the ratchet reset to today's true count. Separately, the full tsc OOM on your Mac is because tsconfig.json includes .next/standalone; excluding it is a one-line change and is the path off ignoreBuildErrors, which today hides at least two auth predicates that reference properties that do not exist (they fail closed by luck).

A migration ledger, and one migrations folder

444 SQL files across two folders, 60 duplicate number prefixes (two 314_), 37 un-numbered files, three clear_*.sql scripts that run unscoped DELETE FROM montree_children, a table (montree_english_schedule) the app upserts into that no migration creates, and a montree_migrations table that nothing writes to. You apply migrations by pasting, which is fine, but the paste should end with INSERT INTO montree_migrations (name) VALUES ('346_…') so the database can tell you what it has. Move supabase/migrations/* and the archive into one numbered sequence; move destructive scripts out of the migrations tree entirely.

Retire the old layers on purpose

Legacy Whale routes (62 with no handler auth), the dead 2FA super-admin tables and route, lib/montree/auth-context.ts (authenticates an unsigned base64 blob, unreferenced), lib/montree/db.ts getChildren() (returns every child on the platform, unreferenced), lib/db.ts (silently discards WHERE clauses, one caller), and the eight /api/whale/parent|teacher routes that can never authenticate. Each is harmless today and each has the most guessable name in the repo for a future agent to reach for. Delete them in one commit with a rollback tag, the way you did the storefront cards.

Storage and photos

Child photos live in a public bucket protected only by URL obscurity, while onboarding documents already use authenticated signed URLs. Move montree-media private and serve through the proxy with a session check; this also fixes the deletion gap and the XSS vector at the root rather than the symptom.

Keep the engine honest

Beyond the four fixes above: make the journal append part of the same transaction as the cache write (an RPC that does both), add the unique index on (child_id, work_key), generalise the guard test to every progress table and to RPC calls, and put the nightly health result somewhere a human sees it (a Gmail draft or a line on the tracker screen) — today a red run goes nowhere.

What is not a problem

No hardcoded super-admin password. 870602 appears nowhere in the tree; super-admin uses an env password, timing-safe comparison, a fail-closed limiter and a 12-hour token. My own notes were wrong and I have corrected them.

The dead 2FA tables without RLS are not in production (migration 254's census says so). Refuted.

The path-traversal upload is behind the old admin cookie with zero callers — dead code, not an internet-facing hole. Downgraded.

The health workflow does not 403; the live endpoint returns the app's own 401 without the secret, which is correct.

Clean by inspection: Stripe webhooks, Potato, CMS, Lens proxies, AES-GCM messaging crypto, verify-child-access.ts, secure-code.ts, the CMS/Lens/tracking migrations (RLS on, scoped to authenticated, real CHECKs and FKs).

Method and sources

A code snapshot (app, lib, components, migrations, supabase, db, tests, scripts, workers, workflows; no binaries) was reviewed statically. Six Opus reviewers each took one area and wrote a report with an inventory table; two further Opus reviewers then tried to refute every Critical and High finding, reading each path end-to-end and executing the engine where possible. Nothing in this page was accepted on the first reviewer's word. No live database was queried, which is why item 1 opens with a query for you to run. The eight full reports (4,500 lines, every claim with file and line) are saved in the repo under docs/audits/2026-09-06-code-audit/.
