## 1. The goal, in plain terms

Every Dark Phonics lesson has a "Printables" row. Tredoux wants every book's
row to look as clean and uniform as **ant-on-my-apple** (the reference/gold
standard): a small, fixed set of pills, no leftover/legacy files linked, no
ambiguity about which pill belongs to which book.

Target pill set:

- **A book** (has its own storybook, e.g. the-sat, the-spat, ant-on-my-apple)
  gets 6 pills: `Read-along`, `Print booklet A5`, `Paperwork pack`,
  `Build-it sheet`, `Tracing workbook`, plus a lesson-level `Letter card PDF`.
- **A reader** (`l.reader`, the simpler standalone Easy Readers) gets only
  3 pills: `Paperwork pack`, `Build-it sheet`, `Tracing workbook`. No
  Read-along/Print booklet A5 — the page never links those for readers.

"Tracing workbook" is the interesting one. The *good* version is not a
generic letter-tracing worksheet — it's a full-page-for-page **duplicate of
the real book**, i.e. same cover art, same illustrations, same imposition,
except each sentence is a trace-guide instead of solid print. That's the
"beautiful new tracing book" Tredoux referred to. Two different pipelines
know how to build this (see below); the 11 Easy Readers don't have this
pipeline available to them.

## 2. The 30 books/readers and which pipeline builds each one

There are 30 slugs total in `lib/montree/dark-phonics/lessons.ts` (a `slug:`
per book/reader). They fall into three completely separate build systems.
**None of these systems know about each other** — don't assume a script that
works for one group works for another.

## 5. Operational gotchas (learned the hard way this session — don't relearn them)

- **Bash + heredoc + apostrophes**: a commit message built via
  `git commit -m "$(cat <<'EOF' ... EOF)"` and run through
  `bash -c '...'` (single-quoted at the outer level) breaks if the message
  body contains a literal apostrophe anywhere (e.g. "the-spat's own"), even
  though it's "inside" the heredoc from the inner shell's point of view. Just
  avoid apostrophes in commit messages written this way.
- **Desktop Commander's `start_process` has a hard ~60s ceiling** at the MCP
  transport layer regardless of the `timeout_ms` you request — the tool call
  errors out with a timeout message, but the underlying shell command on the
  Mac keeps running in the background. Don't panic and don't re-run the same
  command. Instead call `list_processes` to confirm it's still alive (CPU
  usage, recognizable args in the command line), then verify completion via
  side channels — file counts/timestamps locally, or `curl -sI` against the
  live bucket URL checking `content-length`/`last-modified` — rather than by
  re-invoking the long command.
- **`publish-static-materials.mjs` takes explicit file paths as positional
  args**, space-separated — there is no `--paths` flag. Always run
  `--dry-run` first and read its printed target list before the real
  publish. Running the script with an unrecognized flag (e.g. `--help`, which
  it doesn't support) silently falls through to its **default** behavior: a
  real, non-dry-run, full scan+upload of the entire
  `public/dark-phonics-materials/` and `public/dark-phonics-books/works/`
  trees. It happened once this session and was killed before finishing —
  assessed as low-risk (idempotent upsert) but don't do it on purpose.
- **Publishing is idempotent** — safe to re-run
  `publish-static-materials.mjs` for the same files if you're ever unsure
  whether an earlier publish finished.
- **Live verification pattern** used throughout, worth reusing:
  `curl -sI "https://montree.xyz/api/montree/media/proxy/bucket/static-assets/dark-phonics-materials/<slug>/<file>.pdf"`
  — check `content-length` matches the local file byte-for-byte and
  `last-modified` is fresh. Then `curl -s https://montree.xyz/montree/library/dark-phonics -o /tmp/dp.html`
  and `grep -o` for `dark-phonics-materials/<slug>/[a-z-]*\.pdf?v=[0-9]*` to
  confirm the live page HTML is actually serving the new cache-buster
  version.
- **Railway deploy polling**: `mcp__Railway__list-deployments` with
  projectId `bb3e138f-8ce5-4c9d-ba89-efce14d08e36`, serviceId
  `7a625d48-3bc5-48c3-b4e9-369b6ddd6475`, environmentId
  `0b5e0827-9121-4b16-941b-83e83028483f`, `limit: 1` — status goes
  BUILDING → DEPLOYING → SUCCESS, ~2–3 minutes end to end.
- **Visual spot-check pattern**: `pdftoppm -png -r 100 <file>.pdf <prefix>`
  on the Mac, then stage the PNGs into the cloud sandbox with
  `device_stage_files` and view with `Read`. Clean up the scratch `_verify/`
  folder afterward — don't leave it in the working tree.
- The working tree has a large, constant amount of unrelated dirty
  files/untracked directories from other concurrent work streams (grace-
  courtesy books, an unrelated "dark-phonics-live" subscription-app project
  under `_dark-phonics-live-handoff/`, evaluation-kit stuff, etc.). **Never
  `git add -A`** — always stage the exact files this task touched, by name.
